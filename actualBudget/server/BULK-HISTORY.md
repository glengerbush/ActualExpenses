# Bulk register changes and engine history

Ticket 13. Public contracts live in `src/openapi.json`; acceptance is `tests/bulk_history.rs` and `../web/tests/bulk-history-browser.mjs`. Existing receipt, field-clock and epoch rules in `CONCURRENCY.md` still apply.

## Public operations

`POST /api/v1/budgets/{budget}/transactions/bulk` accepts `snapshot`, `action` (`update`, `duplicate`, `delete`) and 1–100 distinct transaction `ids`. Updates provide ordinary transaction `fields`; duplicate provides one stable `duplicate_ids` UUID per selected ID. Fields include date, amount, account, payee, category, notes and cleared status. Create metadata before assigning it in bulk. Inline reference creation through ordinary transaction creation remains one undo group.

Optional `notes: {mode, find, use_regex}` supports `replace`, `prepend`, `append`, `find_replace`; replacement text is `fields.notes`. Find/replace matches pinned Actual's global ECMAScript non-Unicode behavior, including capture substitutions, `$$`, `$&`, prefix/suffix and named groups. Literal find escapes the pattern. Empty find preserves notes. Invalid or excessively expensive patterns, excessive replacement output and invalid Unicode results refuse the entire operation explicitly. Existing bounded register regex machinery supplies matching limits and a shared operation budget.

Selection is individual: expanded split children may be selected independently. Parent and child selections are coalesced by aggregate before mutation. Child notes/payee/category/amount changes affect selected children; account/date/cleared changes require their parent. Selected-parent category changes apply to its allocations. Deleting a parent includes every child; deleting selected children requires a valid remaining aggregate (removing all allocations recombines). Duplicating any member copies the whole aggregate once, using the destination UUID associated with its first selected member. Parent plus child selection cannot duplicate twice. Exact final sums are required; intermediate child amounts are not validated separately.

`GET /api/v1/budgets/{budget}/history` returns `data: {undo, redo, limit:20, epoch, edit_clock}`. Each available action is `{id,label}`; unavailable actions are null. `POST .../history/undo` and `/redo` take `{action_id}` identifying the currently advertised action. Concurrent tabs cannot accidentally consume the next action. Successful navigation returns affected transaction count and current history; metadata-only changes can affect zero transaction rows.

Bulk and history require `X-Actual-History-Owner` (UUID); supported existing financial mutations accept it optionally. New clients also capture/send `X-Actual-Budget-Epoch`. Every mutation uses one original idempotency key and edit clock. Original route, body, owner, epoch and clock are retained for exact retry, cancellation (`X-Actual-Cancel-If-Uncommitted`) and receipt lookup (`X-Actual-Receipt-Only`). Owned fingerprints include owner/epoch; headerless legacy fingerprints remain unchanged. Exact existing receipt replay precedes current cursor, snapshot, epoch and conflict checks, including after archive restore.

## Journal ownership and persistence

One browser installation owns one durable engine UUID. An IndexedDB readwrite get-or-create transaction chooses the same winner for simultaneous first tabs over plain HTTP. Legacy localStorage identity is migrated only when the canonical IDB value is absent. All newly owned requests await initialization; already-saved requests keep their captured owner. This is history scoping, not authentication.

The server retains 20 action groups per budget/owner/epoch. New recorded financial changes truncate redo; rejected operations, cancellations, exact replay and navigation do not create or truncate ordinary history. Journal tables are auxiliary engine state: excluded from clone/import/native archives. Epoch changes fence old groups. Financial rows and receipts remain portable. History survives server/browser restarts but does not follow an exported budget to another engine.

Supported current financial boundaries: ordinary create/update/delete/duplicate; split create/replace/recombine/duplicate/delete; bulk; account creation, metadata, organization, closing, reopening and forced deletion; account groups; category/group creation, changes, movement and deletion/reassignment; payees/tags and associated transaction rewrites. Pinned account-close has an internal `withUndo` around local financial changes; external bank unlinking precedes that boundary. Preferences/dashboard presentation are outside this financial history contract. Later financial features must explicitly join the journal and aggregate protection contract before acceptance.

Capture occurs inside the existing receipt transaction, through connection-local triggers on authoritative registered tables. Derived balances, cursors, receipts and bookkeeping are not captured. Before/after values and per-field versions are retained; totals are regenerated after restoration. Capture failures roll back the complete action.

## Observable conflict policy

Ordinary field edits guard the changed fields plus row identity/deletion/aggregate/protection versions. Undoing amount after another device edits notes succeeds, preserving the newer notes. A newer edit to the same amount conflicts even if its value equals the old value. A newer deletion cannot be silently resurrected. The response is `409 history_conflict`; no rows, totals, action cursor or receipt partially commit.

Creation, deletion, account movement and split changes guard complete affected rows, versions and live split membership conservatively. Any newer overlapping member/structure/protection change refuses the whole inverse. An explicit current reconciled flag cannot be bypassed by ordinary history. Owner-scoped version lineage recognizes only the same owner's prior explicit inverse writes, allowing sequential undo/redo while distinguishing independently newer writes. Fresh timestamps are still required. Validation after the complete inverse rejects dangling categories/accounts/groups and broken split sums. Unrelated newer transactions do not prevent undoing a safe account-name change; they do prevent removing a category newly referenced by those transactions.

Browser bulk/history is online-only. The original request, formatting/date context, epoch, owner and clock are persisted before every send, retry and cancellation. A quota/CAS failure blocks transmission; the UI retains recovery actions and confirmed balances. Saved checkpoints advance only after committed storage. A lost success response can be retried after reload without a duplicate financial action. A durable cancellation fences the original identity; it never invents a replacement request.

## Required composition gates

This private slice starts from ordinary/split/register schema 11 and uses provisional migration 012. Integration renumbers it after reconciliation 12 and transfer 13. Reconciliation routes must call `write_owned`; capture includes all member reconciliation versions and account `last_reconciled`. Journal evidence must preserve exact original complete membership/protection, never mint fresh authorization over a newer lock. Transfers require both reciprocal aggregate sets, link identity guards and transfer validation after restoration. Large-split sparse `Change.changes` needs the compatible constructor field and final aggregate checks. These combined workflows are acceptance gates, not covered by ordinary-only evidence. Companion Android stays expense-only; bulk/history changes are observable through its existing read contract.
